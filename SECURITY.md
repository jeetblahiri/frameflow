# Security and data boundaries

The studio is a local-first browser application. It does not send imported project files, camera frames, microphone audio or recordings to an application server. Direct media URL imports use credentials omitted. The optional live browser receives website URLs, clicks, scrolling and typed/pasted input in an isolated server-side Chromium context. It streams rendered frames to the client. It does not receive camera frames, microphone audio, local project files or recorded takes. Sessions have fresh browser state and close on disconnect or after 270 seconds. The default service endpoint is empty. Local tab sharing remains available; third-party embedding is an explicit optional mode and may be refused by site headers. Tab audio is not requested. Camera segmentation uses a local worker, WASM and model. There is no analytics or account backend.

The production build includes a Content Security Policy, local PDF workers/fonts/decoders, self-contained SVG restrictions, bounded ZIP decompression, complete project-model validation and isolated media keys for project imports. Recording chunks and recovery metadata are committed together in IndexedDB transactions. Failed native encoder starts clear only their own empty recovery state.

Dependencies are locked, audited in CI and checked by Dependabot. Production deployment is gated on the tested build, and pull requests do not receive deployment permissions. No credentials belong in the repository or project archives.

Report security defects through the repository's private vulnerability reporting facility when available. Otherwise report a minimal issue without sensitive recordings, documents, credentials or personal data. Include the browser, reproduction steps and affected project version.

Browser storage can be evicted or cleared by the browser or device. Download important recordings and project backups. Real-device recording limits and known feature boundaries are documented in `docs/VALIDATION.md`.

The browser service validates HTTP/HTTPS destinations and routes browser requests through an egress proxy that resolves hostnames, rejects private/reserved/metadata-network addresses, and connects to the checked IP, including HTTPS CONNECT tunnels. Loopback test destinations require a test-only flag and are always disabled on Vercel. Origin checks, per-IP connection rates, two concurrent sessions per instance, bounded messages/frame buffers and session timeouts constrain resource use. These instance limits are not a replacement for account-wide abuse monitoring or service authentication when exposing a multi-user commercial deployment. The renderer runs a real browser; keep the pinned browser dependencies updated.
